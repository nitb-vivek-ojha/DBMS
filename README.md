# DBMS

## A] DATA TYPES IN POSTGRESQL

### 1. Numeric
| Type | Size | Description |
|---|---|---|
| smallint | 2 bytes | useful for small range of numbers (-32,768 to 32,767) |
| integer | 4 bytes | useful for counts & id's (about ±2.1 billion) |
| bigint | 8 bytes | useful for counts & id's on high scale (about ±9.2 quintillion) |
| numeric(p, s) | variable | exact number with total p digits and s digits after the decimal point. It automatically rounds off to s places. Accepts 'NaN', 'Infinity', '-Infinity' |
| real | 4 bytes | approximate (floating point), about 6 significant digits |
| double precision | 8 bytes | approximate (floating point), about 15 significant digits |

📌 NOTE
- The most important rule: never store money in real or double precision. Floating point can't represent 0.1 exactly, so 0.1 + 0.2 becomes 0.30000000000000004. Across millions of IRCTC fares those rounding errors add up. Use numeric(10,2) for fares, or store paise as bigint.
- The precision of real / double precision is counted in **significant digits**, not decimal places. `123456.7` already uses 7 significant digits.

```sql
CREATE TABLE location(
    code        SMALLINT,
    area_no     INTEGER,
    population  BIGINT,
    cost        NUMERIC(8,3),   -- total digits 8 and 3 after decimal
    temperature REAL,
    latitude    DOUBLE PRECISION,
    longitude   DOUBLE PRECISION
);

INSERT INTO location VALUES (1, 500032, 10500000, 12345.6789, 34.5, 17.3850, 78.4867);
-- cost is stored as 12345.679 (rounded to 3 decimal places)

INSERT INTO location (cost) VALUES (123456.7);
-- ERROR: numeric field overflow (6 digits before the decimal, but only 8-3 = 5 are allowed)

SELECT 0.1::REAL + 0.2::REAL AS float_sum,   -- approximately 0.3, but not exact
       0.1::NUMERIC + 0.2::NUMERIC AS exact_sum;  -- exactly 0.3
```

### 2. Auto generated IDs
| Type | Description |
|---|---|
| serial / bigserial | It is only shorthand for "create a sequence and set a default." Anyone can insert their own value and silently get out of sync with the sequence, and the sequence's ownership and permissions are managed separately from the table. |
| IDENTITY | GENERATED ALWAYS AS IDENTITY rejects manual inserts unless you explicitly say OVERRIDING SYSTEM VALUE. That is another invariant enforced by the schema. |

📌 NOTE
- `GENERATED BY DEFAULT AS IDENTITY` also exists. It allows manual values, like serial does, so prefer `ALWAYS`.
- Use `bigint` identity for tables that grow fast (bookings, logs).

```sql
-- Old way
CREATE TABLE trains_old(
    train_id SERIAL PRIMARY KEY,
    name     TEXT
);

INSERT INTO trains_old (train_id, name) VALUES (1, 'Rajdhani');  -- allowed
INSERT INTO trains_old (name) VALUES ('Shatabdi');
-- ERROR: duplicate key, because the sequence also produced 1

-- Modern way
CREATE TABLE trains_new(
    train_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name     TEXT
);

INSERT INTO trains_new (name) VALUES ('Rajdhani');       -- train_id = 1
INSERT INTO trains_new (train_id, name) VALUES (5, 'X');
-- ERROR: cannot insert a non-DEFAULT value into column "train_id"

INSERT INTO trains_new (train_id, name) OVERRIDING SYSTEM VALUE VALUES (5, 'X');  -- allowed explicitly
```

### 3. Text
| Type | Description |
|---|---|
| text | Unlimited length |
| varchar(n) | Upto n characters |
| char(n) | fixed n characters. padded with spaces |

📌 NOTE
- In PostgreSQL, `text` and `varchar` are stored and perform identically. `varchar(255)` gives no speed advantage.
- Prefer `text` and express real rules with `CHECK`, which is more expressive than a length limit.
- Avoid `char(n)`. Its space padding causes confusing comparison bugs.

```sql
CREATE TABLE stations(
    station_code TEXT NOT NULL CHECK (station_code ~ '^[A-Z]{2,5}$'),  -- 2-5 uppercase letters
    name         VARCHAR(100) NOT NULL,
    zone         CHAR(3)
);

INSERT INTO stations VALUES ('HYB', 'Hyderabad Deccan', 'SC');
-- zone is stored as 'SC ' (padded to 3 characters)

INSERT INTO stations VALUES ('hyb', 'Hyderabad', 'SC');
-- ERROR: violates check constraint (lowercase not allowed)

SELECT length(zone), octet_length(zone) FROM stations;
-- length ignores the trailing space for char(n), which is part of the confusion
```

### 4. Date & Time
| Type | Size | Description |
|---|---|---|
| date | 4 bytes | calendar date only (journey date) |
| time | 8 bytes | time of day only (scheduled departure) |
| timestamp | 8 bytes | date + time, **no time zone** (a wall-clock reading) |
| timestamptz | 8 bytes | date + time, an **absolute instant**, stored internally in UTC |
| interval | 16 bytes | a duration, e.g. `'2 hours 15 minutes'` |

📌 NOTE
- Default to `timestamptz` for anything that records *when something happened* (`booked_at`, `created_at`).
- `timestamptz` does not store the time zone. It converts input to UTC and displays it in the session's time zone.
- Plain `timestamp` is ambiguous. An app server in UTC and a laptop in IST will read the same value as two different moments.
- `time` without a zone is fine for timetables. "Departs 06:15" is a local schedule, not an instant.

```sql
CREATE TABLE journeys(
    journey_date   DATE        NOT NULL,
    departure_time TIME        NOT NULL,
    duration       INTERVAL    NOT NULL,
    booked_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

INSERT INTO journeys (journey_date, departure_time, duration)
VALUES ('2026-10-15', '06:15', '8 hours 30 minutes');

-- Arrival = date + time + duration
SELECT journey_date + departure_time + duration AS arrival FROM journeys;
-- 2026-10-15 14:45:00

-- Same instant, displayed in different zones
SET timezone = 'Asia/Kolkata';
SELECT booked_at FROM journeys;   -- e.g. 2026-09-26 18:30:00+05:30
SET timezone = 'UTC';
SELECT booked_at FROM journeys;   -- 2026-09-26 13:00:00+00
```

### 5. Boolean
| Type | Size | Description |
|---|---|---|
| boolean | 1 byte | `true`, `false`, or `NULL` (unknown) |

📌 NOTE
- NULL means "unknown," which gives you three-valued logic. If a flag must always be decided, use `NOT NULL DEFAULT false`.
- `WHERE NOT is_tatkal` does **not** return rows where `is_tatkal` is NULL.

```sql
CREATE TABLE tickets(
    ticket_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    is_tatkal BOOLEAN NOT NULL DEFAULT false
);

INSERT INTO tickets (is_tatkal) VALUES (true), ('yes'), ('0'), (DEFAULT);
-- 'yes', 'y', '1', 'on' are accepted as true; 'no', 'n', '0', 'off' as false

SELECT count(*) FILTER (WHERE is_tatkal) AS tatkal_count FROM tickets;
```

### 6. Fixed set of values (ENUM vs CHECK vs Lookup table)
| Type | Description |
|---|---|
| ENUM | custom type with a fixed list of values. Compact (4 bytes) and sorts in the declared order. Values can be added but are hard to remove or rename |
| CHECK | a text column restricted with `IN (...)`. Simple and easy to change in a migration. A good default |
| Lookup table | a separate table referenced with a foreign key. Best when values carry extra data or change often |

📌 NOTE
- ENUM sorting follows declaration order, not alphabetical order.
- `ALTER TYPE ... ADD VALUE` has transaction restrictions, which matters for migration scripts.

```sql
-- Option A: ENUM
CREATE TYPE booking_status AS ENUM ('CONFIRMED', 'RAC', 'WAITLISTED', 'CANCELLED');

CREATE TABLE bookings_a(
    pnr    TEXT PRIMARY KEY,
    status booking_status NOT NULL
);

ALTER TYPE booking_status ADD VALUE 'CHART_PREPARED' AFTER 'CONFIRMED';

-- Option B: CHECK
CREATE TABLE bookings_b(
    pnr    TEXT PRIMARY KEY,
    status TEXT NOT NULL CHECK (status IN ('CONFIRMED', 'RAC', 'WAITLISTED', 'CANCELLED'))
);

-- Option C: Lookup table
CREATE TABLE booking_statuses(
    code             TEXT PRIMARY KEY,
    display_name     TEXT NOT NULL,
    counts_for_seats BOOLEAN NOT NULL
);

CREATE TABLE bookings_c(
    pnr    TEXT PRIMARY KEY,
    status TEXT NOT NULL REFERENCES booking_statuses(code)
);
```

### 7. UUID
| Type | Size | Description |
|---|---|---|
| uuid | 16 bytes | 128-bit universally unique identifier, e.g. `a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11` |

📌 NOTE
- `gen_random_uuid()` is built in since PostgreSQL 13 (random, version 4).
- Common pattern: `bigint` identity as the internal primary key (small, fast joins) and `uuid` as the public reference shown to users.
- Sequential IDs in URLs leak business volume and let people guess other users' IDs.
- Random UUIDs are scattered across a B-tree index, which makes inserts slower on huge tables. PostgreSQL 18 adds time-ordered `uuidv7()`.

```sql
CREATE TABLE payments(
    payment_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- internal
    public_ref UUID NOT NULL DEFAULT gen_random_uuid() UNIQUE,  -- shown in URLs / receipts
    amount     NUMERIC(10,2) NOT NULL
);

INSERT INTO payments (amount) VALUES (1450.00) RETURNING public_ref;
```

### 8. JSON
| Type | Description |
|---|---|
| json | stores the raw text exactly as given (keeps whitespace, key order, duplicate keys). Slow to query |
| jsonb | stores a parsed binary form. Faster to query, supports GIN indexes and operators like `@>` and `?` |

📌 NOTE
- Almost always choose `jsonb` over `json`.
- JSON is an escape hatch *out of* schema enforcement. Use it for genuinely variable data (e.g. a payment gateway's raw response).
- Data you filter, join, or constrain (age, berth preference) deserves real columns with real constraints.
- `->` returns JSON, `->>` returns text.

```sql
CREATE TABLE gateway_logs(
    log_id  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload JSONB NOT NULL
);

INSERT INTO gateway_logs (payload) VALUES
('{"gateway": "UPI", "status": "SUCCESS", "txn": {"id": "T123", "amount": 1450}}'),
('{"gateway": "CARD", "status": "FAILED", "error_code": "E42"}');

SELECT payload->>'gateway'           AS gateway,     -- text
       payload->'txn'->>'amount'     AS amount,
       payload #>> '{txn,id}'        AS txn_id        -- path access
FROM gateway_logs;

-- Containment: find all failed payments
SELECT * FROM gateway_logs WHERE payload @> '{"status": "FAILED"}';

-- Index that makes @> fast
CREATE INDEX idx_gateway_payload ON gateway_logs USING gin (payload);
```

### 9. Arrays
| Type | Description |
|---|---|
| type[] | any type can be an array, e.g. `text[]`, `integer[]` |

📌 NOTE
- Arrays violate first normal form. You can't put a foreign key on an array element.
- If the values refer to another table (e.g. station IDs), use a junction table like `train_stops`.
- Arrays are fine for small, self-contained value lists.
- PostgreSQL arrays are 1-indexed.

```sql
CREATE TABLE train_schedule(
    train_no     INTEGER PRIMARY KEY,
    running_days TEXT[] NOT NULL
);

INSERT INTO train_schedule VALUES
(12723, '{MON,WED,FRI}'),
(12759, ARRAY['TUE','THU','SAT','SUN']);

SELECT running_days[1] FROM train_schedule;                     -- first element (MON)
SELECT * FROM train_schedule WHERE 'FRI' = ANY(running_days);  -- trains running on Friday
SELECT * FROM train_schedule WHERE running_days @> '{MON,WED}'; -- runs on both days
SELECT train_no, unnest(running_days) AS day FROM train_schedule; -- one row per day
```

### 10. Range types
| Type | Description |
|---|---|
| int4range / int8range | range of integer / bigint |
| numrange | range of numeric |
| daterange | range of dates |
| tsrange / tstzrange | range of timestamp / timestamptz |

📌 NOTE
- Default bounds are `[)`: the lower bound is included and the upper bound is excluded.
- `&&` means overlaps, `@>` means contains.
- Combined with `EXCLUDE USING gist`, ranges enforce "no overlap" rules at the database level.
- Needs the `btree_gist` extension when the constraint mixes ranges with plain `=` columns.

```sql
SELECT int4range(1, 5) && int4range(5, 8);   -- false (5 is excluded from the first range)
SELECT int4range(1, 5) && int4range(4, 8);   -- true
SELECT daterange('2026-10-01', '2026-10-31') @> '2026-10-15'::DATE;  -- true

CREATE EXTENSION IF NOT EXISTS btree_gist;

-- No seat can be booked twice for overlapping segments of the same journey
CREATE TABLE seat_allocations(
    train_id      INTEGER  NOT NULL,
    journey_date  DATE     NOT NULL,
    seat_no       TEXT     NOT NULL,
    from_stop_seq SMALLINT NOT NULL,
    to_stop_seq   SMALLINT NOT NULL CHECK (to_stop_seq > from_stop_seq),
    EXCLUDE USING gist (
        train_id     WITH =,
        journey_date WITH =,
        seat_no      WITH =,
        int4range(from_stop_seq, to_stop_seq) WITH &&
    )
);

INSERT INTO seat_allocations VALUES (12723, '2026-10-15', 'B1-23', 1, 5);  -- OK
INSERT INTO seat_allocations VALUES (12723, '2026-10-15', 'B1-23', 5, 9);  -- OK (gets on where the other gets off)
INSERT INTO seat_allocations VALUES (12723, '2026-10-15', 'B1-23', 3, 7);
-- ERROR: conflicting key value violates exclusion constraint
```
